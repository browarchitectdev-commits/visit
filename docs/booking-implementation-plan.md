# Полная реализация booking-системы для Brow & Lip Studio

## Контекст

Исходим из текущих вводных:

- сайт уже размещён на `Vercel`;
- фронтенд сайта построен на `Astro`;
- основной сценарий записи должен поддерживать `approval-first workflow`;
- `WhatsApp` пока исключаем;
- хотим использовать `Cal.com + Google Calendar`;
- хотим поддержать 2 точки входа:
  - запись через сайт;
  - запись через `Telegram bot`.

Цель системы:

1. Клиент оставляет заявку через сайт или Telegram.
2. Заявка попадает в единый booking-поток.
3. Администратор подтверждает, переносит или отклоняет запись.
4. Клиент получает уведомление в корректном канале:
   - `email` для web;
   - `Telegram` для Telegram-бота.
5. Занятость студии синхронизирована с `Google Calendar`.

---

## Короткий вывод

Лучший реалистичный вариант для этого проекта:

`Astro site on Vercel -> Cal.com -> Google Calendar -> Vercel API -> Email + Telegram`

Где:

- `Cal.com` отвечает за слоты, бронирования и подтверждение;
- `Google Calendar` остаётся рабочим календарём студии;
- `Vercel API` выступает как лёгкий backend-слой;
- `Telegram bot` становится дополнительным каналом записи;
- `email` остаётся обязательным каналом подтверждения для web-заявок.

Это решение хорошо подходит под текущий стек, не требует VPS на старте и позволяет запустить рабочий MVP без построения собственной scheduling-системы.

## Что даёт текущий стек на Vercel

Раз сайт уже находится на `Vercel`, это даёт нам:

- хостинг фронтенда;
- `serverless functions` для backend-логики;
- HTTPS по умолчанию;
- environment variables для секретов;
- удобный деплой webhook endpoint-ов;
- возможность держать сайт и API в одном проекте;
- возможность позже повесить кастомный домен типа `browlipstudio.it`.

Для этого проекта это значит, что на старте не нужен отдельный сервер, если мы строим систему на webhook-подходе.

## Бизнес-логика системы

### Основной принцип

`Cal.com` должен быть `source of truth` для записей.

Это важно, потому что иначе быстро появится хаос:

- часть записей в Telegram;
- часть в ручных сообщениях;
- часть в календаре;
- часть на сайте;
- переносы и подтверждения в разных местах.

Правильная модель:

- `Cal.com` хранит и управляет booking-событием;
- `Google Calendar` отражает фактическую занятость;
- `Vercel API` связывает внешние каналы с booking-процессом;
- `Telegram` и `email` являются каналами коммуникации.

## Целевая архитектура

## Сервисы

### 1. `Astro site`

Нужен для:

- лендинга;
- booking section;
- страницы записи или встроенного booking-flow;
- кнопки перехода в Telegram.

### 2. `Cal.com`

Нужен для:

- управления event types;
- availability;
- ручного подтверждения через `Requires confirmation`;
- переноса/отмены;
- синхронизации с календарём;
- webhook-событий.

### 3. `Google Calendar`

Нужен для:

- отображения реальной занятости;
- избежания пересечений;
- рабочего расписания администратора или мастера.

### 4. `Vercel API`

Нужен для:

- приёма webhook от `Cal.com`;
- логики Telegram-бота;
- отправки писем;
- хранения метаданных заявки;
- маршрутизации событий в нужный канал.

### 5. `Telegram bot`

Нужен для:

- альтернативной записи через мессенджер;
- отправки пользователю статусов заявки;
- напоминаний или подтверждений в будущем.

### 6. `Database`

Рекомендую `Supabase Postgres`.

Нужна для:

- связи booking с каналом клиента;
- хранения `telegram_user_id`;
- хранения статусов;
- лога событий;
- будущей аналитики и админ-инструментов.

### 7. `Email provider`

Рекомендую:

- `Resend`, если нужен современный простой старт;
- или `Brevo`, если хочется маркетинговый и transactional стек в одном сервисе.

## Рекомендованный MVP

Для первой рабочей версии рекомендую такой scope:

1. Сайт получает блок записи.
2. Основная запись идёт через `Cal.com`.
3. `Google Calendar` подключён и синхронизирован.
4. У event type включён `Requires confirmation`.
5. После создания booking `Cal.com` шлёт email клиенту.
6. `Cal.com` шлёт webhook в `Vercel`.
7. `Vercel` сохраняет запись в БД.
8. Администратор подтверждает запись в `Cal.com`.
9. После подтверждения webhook снова приходит в `Vercel`.
10. `Vercel`:
   - обновляет статус в БД;
   - отправляет Telegram-сообщение, если клиент пришёл из бота;
   - при необходимости дублирует email.

Telegram-бот можно добавлять сразу, но запускать систему лучше так, чтобы web booking уже работал независимо от него.

## Как должен работать пользовательский поток

## Поток A: запись через сайт

1. Пользователь открывает главную страницу.
2. Переходит в блок `Prenota una consulenza`.
3. Выбирает услугу, слот, вводит имя, телефон, email и комментарий.
4. `Cal.com` создаёт booking в статусе ожидания подтверждения.
5. Клиент видит сообщение, что заявка получена.
6. Клиент получает email:
   - заявка получена;
   - ожидает подтверждения.
7. Администратор открывает `Cal.com`.
8. Администратор:
   - подтверждает запись;
   - или переносит;
   - или отклоняет.
9. После действия администратора `Cal.com` отправляет webhook.
10. `Vercel API` фиксирует новый статус.
11. Клиент получает итоговое подтверждение по email.

## Поток B: запись через Telegram

1. Пользователь нажимает кнопку `Scrivici su Telegram`.
2. Открывается чат с ботом.
3. Пользователь нажимает `/start`.
4. Бот объясняет сценарий и предлагает начать запись.
5. Бот собирает:
   - имя;
   - телефон;
   - email;
   - услугу;
   - желаемую дату;
   - комментарий.
6. Бот показывает доступные слоты.
7. После выбора слота backend создаёт booking в `Cal.com`.
8. В БД сохраняется связь:
   - `telegram_user_id`;
   - `cal_booking_id`;
   - клиентские данные;
   - статус.
9. Бот пишет пользователю:
   - заявка создана;
   - ожидает подтверждения администратора.
10. Администратор подтверждает или переносит запись в `Cal.com`.
11. `Cal.com` отправляет webhook.
12. `Vercel API` находит связанного Telegram-пользователя и отправляет ему обновление.

## Почему нужен backend

Если оставить только сайт + Cal.com + Google Calendar, то backend не обязателен.

Но как только добавляем Telegram, backend становится практически обязательным, потому что он нужен для:

- webhook от `Telegram`;
- webhook от `Cal.com`;
- хранения связи booking и пользователя;
- отправки сообщений обратно в Telegram;
- дополнительной валидации;
- логирования;
- будущих напоминаний.

Хорошая новость: это не тяжёлый backend. Для вашего проекта достаточно небольшого слоя на `Vercel`.

---

## Размещение backend

### Вариант 1. Прямо в том же проекте на `Vercel`

Это основной рекомендуемый вариант для старта.

Плюсы:

- всё в одном месте;
- один деплой;
- проще управлять env;
- не нужен отдельный сервер;
- хорошо подходит под webhook-based логику.

Минусы:

- не лучший вариант для тяжёлых фоновых процессов;
- если бот станет очень сложным, позже может быть удобнее вынести его отдельно.

### Вариант 2. Отдельный backend-сервис

Например:

- `Railway`;
- `Render`;
- `Fly.io`;
- VPS.

Это понадобится позже, если:

- бот станет сложнее;
- появятся cron jobs;
- нужна постоянная обработка очередей;
- появится своя админка и больше custom-логики.

### Вывод

Для `v1` и `v2` я рекомендую держать backend прямо на `Vercel`.

## Назначение API-роутов

### `/api/webhooks/cal`

Принимает события от `Cal.com`.

Нужен для:

- создания записи в локальной БД;
- обновления статуса;
- отправки уведомлений;
- логирования.

Ожидаемые типы событий:

- booking created;
- booking confirmed;
- booking rescheduled;
- booking cancelled;
- booking rejected, если используется такой сценарий.

### `/api/webhooks/telegram`

Принимает обновления от `Telegram Bot API`.

Нужен для:

- команд `/start`, `/help`, `/book`;
- диалогов с пользователем;
- обработки callback-кнопок;
- сохранения состояния диалога.

### `/api/bookings/slots`

Нужен для выдачи доступных слотов Telegram-боту.

Логика:

- получает услугу и дату;
- запрашивает availability из `Cal.com`;
- возвращает пользователю список слотов.

### `/api/bookings/create`

Нужен для создания booking из Telegram flow.

Логика:

- принимает собранные данные клиента;
- создаёт заявку в `Cal.com`;
- сохраняет локальную запись в БД;
- возвращает результат боту.

### `/api/bookings/status`

Опциональный endpoint для будущей mini-admin-панели или внутренней диагностики.

## Как настроить Cal.com

## 1. Создать event types

Рекомендую минимум 2 event types:

- `Permanent Brows`
- `Permanent Lips`

Если длительность сильно отличается, лучше делать разные event types.

Если позже появятся:

- touch-up;
- consultation;
- correction;

их тоже лучше выделить отдельно.

## 2. Подключить Google Calendar

Календарь должен быть подключён так, чтобы занятость мастера или студии блокировала недоступные слоты.

## 3. Включить `Requires confirmation`

Это ключ к вашему сценарию.

Результат:

- клиент не получает мгновенное окончательное подтверждение;
- запись сначала ждёт проверки администратором;
- администратор может подтвердить, отклонить или предложить перенос.

## 4. Настроить availability

Нужно определить:

- рабочие дни;
- интервалы;
- buffer между клиентами;
- минимальное время до ближайшей записи;
- ограничения на запись в тот же день.

## 5. Настроить вопросы booking-формы

Рекомендую собирать:

- имя;
- email;
- телефон;
- выбранную услугу;
- комментарий;
- возможно, язык общения.

## 6. Настроить webhooks

Нужно добавить webhook на `Vercel` endpoint:

- `https://your-domain/api/webhooks/cal`

## Как настроить Telegram-бота

## Роль бота

Бот не должен становиться отдельной booking-системой.

Он должен быть интерфейсом к тому же booking-ядру.

То есть бот:

- собирает данные;
- показывает слоты;
- создаёт заявку через backend;
- ждёт события от `Cal.com`;
- уведомляет клиента.

## Команды бота

Рекомендую минимум:

- `/start`
- `/book`
- `/services`
- `/help`

## Состояния диалога

Минимальный state machine:

- `idle`
- `waiting_service`
- `waiting_date`
- `waiting_slot`
- `waiting_name`
- `waiting_phone`
- `waiting_email`
- `waiting_notes`
- `confirming`
- `completed`

## UX бота

Лучше не просить всё свободным текстом.

Лучше использовать:

- inline buttons для выбора услуги;
- inline buttons для выбора даты;
- inline buttons для выбора слота.

Свободный текст оставить для:

- имени;
- телефона;
- комментария.

## Критичное ограничение Telegram

Бот может писать пользователю только если пользователь сам начал чат с ботом.

Для вашего сценария это нормально, потому что запись через Telegram всегда начинается с `/start`.

---

## Как будет работать связь `Cal.com -> Telegram`

Сценарий после подтверждения:

1. Администратор подтверждает запись в `Cal.com`.
2. `Cal.com` отправляет webhook в `/api/webhooks/cal`.
3. Backend проверяет тип события.
4. Backend находит локальную запись по `cal_booking_id`.
5. Если `source = telegram`, backend отправляет сообщение пользователю через Telegram Bot API.
6. Если `source = web`, backend отправляет email или просто пишет в лог.

Это основной механизм интеграции.

То есть прямого встроенного маршрута `Cal.com -> Telegram user` как готовой кнопки нам не нужно ждать. Это легко решается через webhook и наш backend.

## Email-стратегия

Даже если основной акцент будет на Telegram, я рекомендую всё равно собирать `email` как обязательное поле.

Почему:

- это fallback-канал;
- он удобен для подтверждений и переносов;
- он полезен для клиента;
- он упрощает ручную работу администратора;
- он снижает зависимость от конкретного мессенджера.

### Какие письма нужны

- `booking_received`
- `booking_confirmed`
- `booking_rescheduled`
- `booking_cancelled`

### Когда отправлять письма

Для web-потока:

- всегда.

Для Telegram-потока:

- желательно тоже отправлять, если email указан.

## Уведомления администратору

Рекомендую сделать 2 канала:

### 1. Основной

Работа с записью внутри `Cal.com`.

### 2. Дополнительный

Уведомления о новых заявках в Telegram admin chat.

Это удобно, потому что администратор быстро узнает:

- кто записался;
- на какую услугу;
- на какой слот;
- откуда пришла заявка.

Но action всё равно лучше завершать в `Cal.com`, а не в Telegram.

## Основные риски

## 1. Расхождение статусов

Если хранить часть данных только в Telegram, а часть только в `Cal.com`, быстро появится рассинхрон.

Решение:

- всегда привязывать локальную запись к `cal_booking_id`;
- финальный статус брать из booking-событий `Cal.com`.

## 2. Недостаток данных от клиента

Если в Telegram не собирать email и телефон, администратору будет неудобно работать.

Решение:

- сделать `phone` и `email` обязательными даже в Telegram flow.

## 3. Ошибки webhook

Webhook может не дойти или обработаться с ошибкой.

Решение:

- логировать все входящие события;
- хранить event log;
- предусмотреть idempotency и retry-логику.

## 4. Слишком сложный бот на старте

Если перегрузить бота сценариями, запуск затянется.

Решение:

- сначала сделать простую воронку:
  - услуга;
  - дата;
  - слот;
  - имя;
  - телефон;
  - email;
  - комментарий.

## Порядок реализации в проекте

Если делать это по уму и без перегруза, я бы шёл так:

1. Сделать `booking`-секцию на сайте.
2. Подключить `Cal.com`.
3. Завести `Google Calendar`.
4. Поднять `Vercel` webhook для `Cal.com`.
5. Добавить БД и лог booking-событий.
6. Подключить email provider.
7. После этого делать Telegram-бота.
8. Затем добавлять admin notifications и полировку.

Такой порядок самый безопасный: сначала запускается запись через сайт, потом только добавляется Telegram как второй входной канал.

Для Brow & Lip Studio я рекомендую такую реализацию:

`Сайт на Vercel -> Cal.com с Requires confirmation -> Google Calendar -> Vercel API -> Email -> Telegram bot`

Это даёт:

- красивую и понятную запись с сайта;
- ручное подтверждение администратором;
- синхронизацию с реальным календарём;
- канал записи через Telegram;
